# BitScope - 한국 암호화폐 거래소 포트폴리오 통합 조회 웹 서비스 요구사항 문서

## 소개

BitScope는 한국 3대 암호화폐 거래소(업비트, 빗썸, 코인원)의 포트폴리오를 하나의 대시보드에서 통합 조회할 수 있는 웹 서비스이다. 사용자는 각 거래소의 Read-Only API 키를 등록하여 보유 자산을 실시간으로 확인하고, 거래소 간 자산 분포, 수익률 분석, 시세 차이(김치 프리미엄) 모니터링 등 다양한 인사이트를 얻을 수 있다.

**보안 아키텍처 핵심 원칙:** 거래소 API 호출 시 API Key(Secret Key)는 절대 브라우저 밖으로 전송되지 않는다. 클라이언트(브라우저)에서 거래소별 인증 방식에 따라 API 요청을 서명하며, Next.js Route Handler가 CORS 프록시로서 클라이언트가 서명한 요청을 거래소에 릴레이(전달)만 수행한다. NestJS는 백그라운드 서비스(WebSocket 시세 수신, DB 저장, 알림 모니터링, 정기 리포트 생성 등)에 집중한다. 이를 통해 서버가 API Key 원문을 보유하지 않으므로 서버 침해 시에도 API Key가 유출되지 않는다.

기술적으로 Next.js(App Router) + TypeScript 기반의 모노레포(Turborepo + pnpm) 구조를 채택한다. OCI Always Free Tier VM(ARM)에 Next.js(standalone, port 3000)와 NestJS(port 4000)를 함께 배포하며, nginx를 리버스 프록시로 사용한다. 초기에는 도메인 없이 IP + HTTP로 시작 가능하며(API Key가 서버로 전송되지 않으므로 HTTP에서도 보안상 문제 없음), 도메인 확보 후 Let's Encrypt SSL을 적용한다. 같은 서버에서 Web(Next.js)과 WAS(NestJS)가 동작하므로 CORS 문제가 발생하지 않는다. 향후 해외 거래소 확장, 거래 기능 지원, 온체인 지갑 조회 등을 계획하고 있다.

**인프라 구성:**
- OCI Free VM (ARM) + Docker Compose: nginx (리버스 프록시, 도메인 확보 후 SSL) + Next.js (standalone) + NestJS + MySQL

## 요구사항

### 1. 거래소 API 키 관리

**사용자 스토리:** 사용자로서, 각 거래소(업비트, 빗썸, 코인원)의 API 키를 안전하게 등록/관리하고 싶다. 이를 통해 내 자산 정보를 자동으로 불러올 수 있다.

#### 수용 기준

1. WHEN 사용자가 거래소 API 키 등록 페이지에 접근하면, 시스템 SHALL 업비트, 빗썸, 코인원 3개 거래소의 API 키 입력 폼을 표시한다.
2. WHEN 사용자가 API 키(Access Key, Secret Key)를 입력하고 등록 버튼을 클릭하면, 시스템 SHALL 해당 키의 유효성을 거래소 API를 통해 검증한 뒤 결과를 표시한다.
3. IF API 키 검증이 실패하면, 시스템 SHALL 실패 원인(잘못된 키, 권한 부족, 네트워크 오류 등)을 사용자에게 명확히 안내한다.
4. WHEN API 키가 성공적으로 등록되면, 시스템 SHALL 지갑 서명 기반으로 도출된 암호화 키를 사용하여 해당 API 키를 AES 암호화한 뒤 localStorage에 저장한다. 이때 모든 localStorage 데이터(API 키, 설정, 워치리스트 등)는 연결된 지갑 주소별로 분리 저장하여(예: `bitscope:{지갑주소}:apikey:upbit`) 계정 간 데이터가 격리되도록 한다.
5. WHEN 사용자가 등록된 API 키를 삭제하면, 시스템 SHALL 해당 키와 관련된 모든 데이터를 즉시 삭제한다.
6. WHILE API 키가 등록되어 있는 동안, 시스템 SHALL API 키의 Secret Key를 마스킹 처리하여 표시한다 (예: `****abcd`).
7. IF 사용자가 Read-Only 권한이 아닌 API 키를 등록하려 하면, 시스템 SHALL 보안 경고를 표시하고 Read-Only 권한으로 재발급할 것을 권장한다.
8. WHEN 사용자가 거래소별 API 키 발급 방법을 모를 때, 시스템 SHALL 각 거래소별 API 키 발급 가이드 링크 또는 단계별 안내를 제공한다.
9. WHEN 사용자가 등록된 API 키 목록을 조회하면, 시스템 SHALL 거래소명, 등록일, 연결 상태를 표시한다.

---

### 2. 통합 포트폴리오 대시보드

**사용자 스토리:** 사용자로서, 여러 거래소에 분산된 내 암호화폐 자산을 하나의 화면에서 통합 조회하고 싶다. 이를 통해 전체 자산 현황을 한눈에 파악할 수 있다.

#### 수용 기준

1. WHEN 사용자가 대시보드 페이지에 접근하면, 시스템 SHALL 등록된 모든 거래소의 자산을 통합하여 총 평가금액(KRW), 총 투자금액, 총 손익, 총 수익률을 표시한다.
2. WHEN 대시보드가 로드되면, 시스템 SHALL 거래소별 보유 코인 목록(코인명, 수량, 매수 평균가, 현재가, 평가금액, 수익률)을 테이블 형태로 표시한다.
3. WHEN 동일한 코인을 여러 거래소에서 보유하고 있으면, 시스템 SHALL 코인별 통합 보유 현황(총 수량, 가중 평균 매수가, 총 평가금액)과 거래소별 개별 내역을 모두 제공한다.
4. WHEN 대시보드가 활성 상태이면, 시스템 SHALL 일정 주기(기본 30초)로 자산 정보를 자동 갱신한다.
5. WHEN 사용자가 수동 새로고침 버튼을 클릭하면, 시스템 SHALL 즉시 모든 거래소의 최신 자산 정보를 조회하여 반영한다.
6. IF 특정 거래소의 API 호출이 실패하면, 시스템 SHALL 해당 거래소의 데이터를 마지막 성공 시점으로 표시하고, 오류 상태를 시각적으로 구분하여 안내하되, 나머지 거래소의 데이터는 정상적으로 표시한다.
7. WHEN 대시보드가 로드되면, 시스템 SHALL 자산 분포를 도넛/파이 차트로 시각화한다 (코인별 비중, 거래소별 비중).
8. WHEN 사용자가 특정 코인을 선택하면, 시스템 SHALL 해당 코인의 거래소별 보유 상세(수량, 매수가, 현재가, 수익률)를 비교하여 표시한다.
9. WHEN 사용자가 정렬 기준(평가금액, 수익률, 코인명 등)을 변경하면, 시스템 SHALL 즉시 테이블을 재정렬하여 표시한다.
10. WHEN 사용자가 필터(거래소별, 수익/손실 구분)를 적용하면, 시스템 SHALL 조건에 맞는 자산만 표시한다.
11. WHEN 자산 데이터 로딩 중에는, 시스템 SHALL 거래소별 로딩 상태를 개별적으로 표시한다.

### 3. 거래소 간 시세 차이(김치 프리미엄) 분석

**사용자 스토리:** 사용자로서, 동일 코인의 거래소 간 시세 차이를 실시간으로 확인하고 싶다. 이를 통해 재정거래 기회를 포착하거나 시장 상황을 판단할 수 있다.

#### 수용 기준

1. WHEN 김프 분석 페이지에 접근하면, 시스템 SHALL 주요 코인(BTC, ETH 등)의 3개 거래소 간 실시간 시세를 비교 테이블로 표시한다.
2. WHEN 거래소 간 시세 차이가 발생하면, 시스템 SHALL 가격 차이(절대값, 백분율)를 계산하여 표시한다.
3. WHEN 시세 차이가 사용자 설정 임계값을 초과하면, 시스템 SHALL 시각적 하이라이트(색상 강조)로 해당 항목을 표시한다.
4. WHEN 김프 분석 페이지가 활성 상태이면, 시스템 SHALL 실시간(WebSocket 또는 5초 이내 폴링)으로 시세를 업데이트한다.
5. IF 해외 거래소(바이낸스 등) 시세 데이터가 활용 가능하면, 시스템 SHALL 국내-해외 거래소 간 김치 프리미엄(%)을 산출하여 표시한다.
6. WHEN 사용자가 특정 코인의 김프 이력을 조회하면, 시스템 SHALL 최근 24시간/7일/30일간의 김프 추이를 차트로 표시한다.

### 4. 포트폴리오 성과 분석

**사용자 스토리:** 사용자로서, 내 포트폴리오의 시간에 따른 성과를 분석하고 싶다. 이를 통해 투자 전략을 개선할 수 있다.

#### 수용 기준

1. WHEN 성과 분석 페이지에 접근하면, 시스템 SHALL 총 자산 평가금액의 시계열 추이 차트(일/주/월 단위)를 표시한다.
2. WHEN 성과 분석 데이터가 로드되면, 시스템 SHALL 총 투자 원금, 현재 평가금액, 총 손익(금액 및 비율)을 요약하여 표시한다.
3. WHEN 사용자가 특정 기간을 선택하면, 시스템 SHALL 해당 기간의 수익률, 최대 수익, 최대 손실을 계산하여 표시한다.
4. WHEN 성과 분석 페이지가 로드되면, 시스템 SHALL 코인별 수익률 랭킹(최고 수익 코인 TOP 5, 최대 손실 코인 TOP 5)을 표시한다.
5. IF 충분한 이력 데이터가 축적되면, 시스템 SHALL 벤치마크(BTC, 코스피 등) 대비 포트폴리오 성과를 비교 차트로 제공한다.
6. WHEN 사용자가 기간별 리포트를 요청하면, 시스템 SHALL 일간/주간/월간 포트폴리오 요약 리포트를 생성하여 표시한다.
7. WHEN 사용자가 개별 코인을 선택하면, 시스템 SHALL 해당 코인의 매수 시점 대비 수익률 변화를 표시한다.
8. WHEN 사용자가 특정 기간을 선택하면, 시스템 SHALL 해당 기간의 실현 손익과 미실현 손익을 구분하여 표시한다.
9. WHEN 사용자가 대시보드에 접속하면, 클라이언트 SHALL 현재 포트폴리오 스냅샷(보유 자산, 평가금액, 수익률 등)을 NestJS 백엔드에 전송하여 DB에 저장한다. 서버에 API Key가 없으므로 서버 측 cron 방식의 자동 수집은 불가하며, 사용자가 서비스를 사용할 때마다 자연스럽게 스냅샷이 축적되는 구조이다.
10. WHEN 성과 분석 페이지에서 이력 데이터를 조회하면, 시스템 SHALL 클라이언트 접속 시 축적된 DB 스냅샷 데이터를 기반으로 시계열 분석을 제공한다.

### 5. 실시간 시세 및 마켓 정보

**사용자 스토리:** 사용자로서, 보유하지 않은 코인을 포함한 전체 마켓 시세를 실시간으로 확인하고 싶다. 이를 통해 시장 동향을 파악하고 투자 결정을 내릴 수 있다.

#### 수용 기준

1. WHEN 마켓 페이지에 접근하면, 시스템 SHALL 거래소별 전체 코인 시세(현재가, 24시간 변동률, 거래량)를 목록으로 표시한다.
2. WHEN 마켓 페이지가 활성 상태이면, 시스템 SHALL 실시간으로 시세를 업데이트한다.
3. WHEN 사용자가 특정 코인을 검색하면, 시스템 SHALL 코인명 또는 티커로 검색 결과를 즉시 필터링하여 표시한다.
4. WHEN 사용자가 특정 코인의 상세 정보를 조회하면, 시스템 SHALL 가격 차트(캔들스틱), 호가 정보, 최근 체결 내역을 표시한다.
5. WHEN 마켓 페이지가 로드되면, 시스템 SHALL 거래량 상위, 상승률 상위, 하락률 상위 코인을 하이라이트 섹션으로 제공한다.

### 6. 알림 및 모니터링

**사용자 스토리:** 사용자로서, 특정 코인 가격 도달이나 김프 변동 시 즉시 알림을 받고 싶다. 이를 통해 중요한 시장 변동을 놓치지 않을 수 있다.

#### 수용 기준

1. WHEN 사용자가 가격 알림을 설정하면(코인, 목표가, 조건), 시스템 SHALL 해당 조건 충족 시 브라우저 알림을 전송한다.
2. WHEN 김프(거래소 간 시세 차이)가 사용자 설정 임계값을 초과하면, 시스템 SHALL 알림을 전송한다.
3. WHEN 사용자가 알림 목록 페이지에 접근하면, 시스템 SHALL 활성/비활성 알림 설정 목록과 최근 발생한 알림 이력을 표시한다.
4. IF 브라우저 알림 권한이 거부된 상태이면, 시스템 SHALL 인앱 알림(토스트, 배지)으로 대체하여 표시한다.
5. WHEN 알림이 발생하면, 시스템 SHALL 알림 이력을 기록하여 사용자가 이후에 확인할 수 있도록 저장한다.
6. WHILE 시스템이 운영 중일 때, NestJS 백그라운드 서비스 SHALL 가격 모니터링 프로세스를 상시 운영하여 거래소 공개 API(REST 및 WebSocket)를 통해 실시간 시세를 감시한다 (시세 데이터는 공개 데이터이므로 API Key가 불필요하다).
7. WHEN 가격 모니터링 프로세스가 사용자 설정 조건(가격 알림, 김프 알림) 충족을 감지하면, NestJS 백그라운드 서비스 SHALL 즉시 해당 사용자에게 알림을 발송한다.

### 7. 자동 리포트 생성 및 데이터 내보내기

**사용자 스토리:** 사용자로서, 내 포트폴리오 현황을 리포트로 생성하고 데이터를 외부로 내보내고 싶다. 이를 통해 별도 분석 도구에서 활용하거나 투자 상황을 기록할 수 있다.

#### 수용 기준

1. WHEN 사용자가 리포트 생성을 요청하면, 시스템 SHALL 현재 시점의 포트폴리오 스냅샷(보유 자산, 평가금액, 수익률, 자산 분포)을 리포트로 생성한다.
2. WHEN 리포트가 생성되면, 시스템 SHALL 리포트를 PDF 또는 이미지 형식으로 다운로드 가능하도록 제공한다.
3. IF 사용자가 정기 리포트를 설정하면(일간/주간/월간), NestJS 백그라운드 서비스 SHALL 스케줄러(cron)를 통해 설정된 주기에 맞춰 자동으로 리포트를 생성하고 사용자에게 알림을 전송한다.
4. WHEN 리포트가 생성되면, 시스템 SHALL 이전 리포트 대비 변동 사항(자산 증감, 신규 편입/편출 코인)을 하이라이트하여 포함한다.
5. WHEN 사용자가 리포트 이력 페이지에 접근하면, 시스템 SHALL 과거 생성된 리포트 목록을 시간순으로 표시하고 재조회를 지원한다.
6. WHEN 사용자가 데이터 내보내기를 요청하면, 시스템 SHALL 현재 포트폴리오 스냅샷을 CSV, JSON 형식으로 제공한다.
7. WHEN 사용자가 거래 내역 내보내기를 요청하면, 시스템 SHALL 선택한 기간의 거래 내역을 CSV 형식으로 제공한다.
8. WHEN 사용자가 설정 백업을 요청하면, 시스템 SHALL API 키를 제외한 사용자 설정(알림, 목표 비중 등)을 JSON 형식으로 내보낸다.
9. WHEN 사용자가 설정 복원을 요청하면, 시스템 SHALL 백업 파일을 검증한 후 설정을 복원한다.

### 8. 사용자 인증 및 데이터 보안

**사용자 스토리:** 사용자로서, Web3 지갑을 통해 별도 회원가입 없이 서비스에 접속하고, 내 거래소 API 키가 클라이언트에서 안전하게 암호화되어 보호되길 원한다. 이를 통해 서버에 민감한 데이터를 맡기지 않고도 서비스를 이용할 수 있다.

#### 수용 기준

**[지갑 연결 및 인증]**

1. WHEN 사용자가 서비스에 접근하면, 시스템 SHALL EIP-1193 표준 기반의 Web3 지갑(MetaMask 등) 연결을 통한 인증을 제공한다.
2. WHEN 사용자가 지갑을 연결하면, 시스템 SHALL 지갑 주소를 사용자 식별자로 사용하며, 별도의 서버사이드 인증이나 데이터베이스 저장 없이 인증을 완료한다.
3. IF 브라우저에 호환 가능한 Web3 지갑이 설치되어 있지 않으면, 시스템 SHALL MetaMask 설치 안내 및 설치 링크를 제공한다.

**[API 키 암호화 - 지갑 서명 기반]**

4. WHEN 사용자가 최초로 API 키를 등록하면, 시스템 SHALL crypto.randomUUID()를 사용하여 고유한 nonce를 생성한다.
5. WHEN nonce가 생성되면, 시스템 SHALL "BitScope:encrypt:{지갑주소}:{nonce}" 형태의 서명 메시지를 구성하고, personal_sign(EIP-191)을 통해 사용자에게 서명을 요청한다.
6. WHEN 지갑 서명이 완료되면, 시스템 SHALL 서명 결과를 crypto-js 등 JS 암호화 라이브러리를 사용하여 SHA-256 해시 처리하고 AES 암호화 키를 도출한다 (HTTPS 없이도 동작 가능하도록 Web Crypto API 대신 JS 라이브러리를 사용한다).
7. WHEN 암호화 키가 도출되면, 시스템 SHALL 해당 키로 API 키를 AES 방식으로 암호화하여 localStorage에 저장한다.
8. WHEN 암호화된 API 키가 저장되면, 시스템 SHALL nonce를 암호화된 API 키와 함께 localStorage에 평문으로 저장한다 (nonce 자체는 비밀 정보가 아니며, 서명 메시지를 설치마다 고유하게 만들어 다른 사이트의 서명 재사용을 차단하는 역할을 한다).

**[클라이언트 세션 관리]**

9. WHEN 사용자가 지갑을 연결하고 세션을 시작하면, 시스템 SHALL 1회 서명을 통해 암호화 키를 도출하고, 해당 키를 JS 메모리(변수)에 보관한다 (가장 안전한 방식).
10. IF 시스템이 편의성과 보안의 절충을 선택하는 경우, 시스템 SHALL 도출된 암호화 키를 sessionStorage에 보관할 수 있으며, 이 경우 탭을 닫을 때 자동으로 삭제된다.
11. WHEN 페이지가 새로고침되면 (JS 메모리 보관 방식의 경우), 시스템 SHALL 사용자에게 재서명을 요청하여 암호화 키를 다시 도출한다.

**[지갑 변경 시 처리]**

12. WHEN 사용자가 지갑 주소를 변경하면, 시스템 SHALL 기존 암호화된 API 키가 복호화 불가능함을 감지한다.
13. IF 지갑 변경으로 인해 기존 API 키를 복호화할 수 없으면, 시스템 SHALL 사용자에게 API 키 재등록이 필요하다는 안내를 명확하게 제공한다.

**[통신 보안 및 API 키 보호]**

14. WHILE 시스템이 운영 중일 때, 시스템 SHALL 도메인 확보 후 HTTPS(TLS 1.2 이상)를 적용한다. 초기에는 IP + HTTP로 운영 가능하며, API Key가 서버로 전송되지 않으므로 HTTP 환경에서도 보안상 문제가 없다.
15. WHEN 거래소 API 호출이 수행되면, Next.js Route Handler SHALL CORS 프록시로서 클라이언트가 서명한 요청을 거래소에 릴레이하며, API Key 원문은 서버로 전송하지 않는다.
16. WHILE 시스템이 운영 중일 때, API Key(Secret Key) SHALL 절대 브라우저 밖으로 전송되지 않으며, 클라이언트 로그에도 API Key 원문을 기록하지 않는다.
17. WHEN 클라이언트가 거래소 API 요청을 서명할 때, 시스템 SHALL nonce/timestamp 기반으로 서명하여 서명된 요청이 일회성이 되도록 한다. 이를 통해 서명된 요청이 탈취되더라도 재사용이 불가능하다.

**[향후 확장 연결]**

18. WHEN Web3 지갑 연결 기능이 구현되면, 시스템 SHALL 향후 온체인 지갑 자산 조회 기능으로의 확장이 자연스럽게 가능하도록 지갑 연결 인터페이스를 설계한다.

### 9. 반응형 UI 및 사용자 경험

**사용자 스토리:** 사용자로서, PC와 모바일 기기 어디서든 편리하게 포트폴리오를 확인하고 싶다. 이를 통해 장소와 기기에 구애받지 않고 자산을 관리할 수 있다.

#### 수용 기준

1. WHEN 사용자가 모바일 기기(화면 너비 768px 이하)에서 접근하면, 시스템 SHALL 모바일에 최적화된 레이아웃을 제공한다.
2. WHEN 사용자가 데스크톱(화면 너비 1024px 이상)에서 접근하면, 시스템 SHALL 사이드바 네비게이션과 넓은 데이터 테이블을 포함한 다중 패널 레이아웃을 제공한다.
3. WHEN 사용자가 다크 모드/라이트 모드를 전환하면, 시스템 SHALL 즉시 테마를 변경하여 적용한다.
4. IF 사용자의 시스템 설정이 다크 모드이면, 시스템 SHALL 기본값으로 다크 모드를 적용한다.
5. WHEN 데이터가 로딩 중이면, 시스템 SHALL 스켈레톤 UI 또는 로딩 인디케이터를 표시하여 사용자에게 로딩 상태를 안내한다.
6. WHEN 거래소 API 호출 중 오류가 발생하면, 시스템 SHALL 사용자 친화적인 오류 메시지와 재시도 옵션을 제공한다.
7. WHEN 숫자 데이터(금액, 수익률 등)가 표시되면, 시스템 SHALL 적절한 포맷(천 단위 구분, 소수점, 통화 기호 등)을 적용한다.
8. WHEN 수익이면 시스템 SHALL 녹색/파란색 계열로, 손실이면 시스템 SHALL 빨간색 계열로 색상을 구분하여 표시한다.
9. WHEN 사용자가 언어를 변경하면, 시스템 SHALL 한국어와 영어를 지원한다.

### 10. 관심 코인 및 워치리스트

**사용자 스토리:** 사용자로서, 보유하지 않은 코인도 관심 목록에 추가하여 시세를 추적하고 싶다. 이를 통해 잠재적 투자 대상을 모니터링할 수 있다.

#### 수용 기준

1. WHEN 사용자가 특정 코인을 관심 목록에 추가하면, 시스템 SHALL 해당 코인을 워치리스트에 저장하고 대시보드 상단 또는 별도 섹션에 표시한다.
2. WHEN 워치리스트가 표시되면, 시스템 SHALL 각 코인의 현재가, 24시간 변동률, 거래량을 실시간으로 업데이트한다.
3. WHEN 사용자가 관심 코인에 대해 가격 알림을 설정하면, 시스템 SHALL 해당 조건 도달 시 알림을 전송한다.
4. WHEN 사용자가 워치리스트에서 코인을 제거하면, 시스템 SHALL 즉시 해당 코인을 관심 목록에서 삭제한다.

### 11. 초기 온보딩 경험

**사용자 스토리:** 사용자로서, 서비스를 처음 사용할 때 쉽고 빠르게 설정을 마치고 싶다. 이를 통해 복잡한 설정 없이 바로 포트폴리오를 조회할 수 있다.

#### 수용 기준

1. WHEN 사용자가 최초 로그인하면, 시스템 SHALL 단계별 온보딩 가이드(거래소 선택 -> API 키 입력 -> 자산 조회 확인)를 제공한다.
2. WHEN 온보딩 중 사용자가 특정 거래소를 건너뛰면, 시스템 SHALL 해당 거래소 없이도 나머지 거래소의 포트폴리오를 정상적으로 표시한다.
3. IF 사용자가 어떤 거래소의 API 키도 등록하지 않으면, 시스템 SHALL 데모 데이터를 활용한 미리보기 모드를 제공하여 서비스 기능을 체험하게 한다.
4. WHEN 온보딩이 완료되면, 시스템 SHALL 즉시 대시보드로 이동하여 통합 자산 현황을 표시한다.

### 12. 거래소 API 연동

**사용자 스토리:** 서비스 운영자로서, 각 거래소 API를 안정적으로 연동하되, API Key 원문이 서버에 전달되지 않는 안전한 구조를 유지하고 싶다. 이를 통해 사용자에게 정확하고 빠른 데이터를 제공하면서도 보안을 보장할 수 있다.

#### 수용 기준

**[클라이언트 측 요청 서명]**

1. WHEN 사용자의 포트폴리오/잔고 등 인증이 필요한 거래소 API를 호출할 때, 클라이언트(브라우저) SHALL 거래소별 인증 방식에 따라 API 요청을 서명한다 (업비트: JWT 토큰 생성, 빗썸/코인원: HMAC-SHA512 서명).
2. WHEN 클라이언트가 서명된 요청을 생성하면, 시스템 SHALL API Key(Secret Key) 원문을 서버로 전송하지 않고, 서명된 요청(헤더 및 페이로드)만 Next.js Route Handler에 전달한다.

**[Next.js CORS 프록시 / 릴레이]**

3. WHEN Next.js Route Handler가 클라이언트로부터 서명된 거래소 API 요청을 수신하면, Next.js Route Handler SHALL 해당 요청을 거래소 API에 그대로 릴레이(전달)하고 응답을 클라이언트에 반환한다.
4. WHEN 거래소 API 응답을 수신하면, Next.js Route Handler SHALL 응답 데이터를 통일된 내부 데이터 모델로 정규화하여 클라이언트에 전달한다.
5. WHEN 동일 데이터에 대한 반복 요청이 발생하면, Next.js Route Handler SHALL 적절한 캐싱 전략(기본 TTL 10초)을 적용하여 불필요한 거래소 API 호출을 줄인다.
6. WHEN 거래소 API 호출 시 Rate Limit에 도달하면, Next.js Route Handler SHALL 지수 백오프(Exponential Backoff) 전략을 적용하여 재시도를 수행한다.
7. WHEN 거래소 API 응답이 10초 이내에 수신되지 않으면, Next.js Route Handler SHALL 타임아웃 처리를 하고 클라이언트에 오류를 반환한다.
8. IF 특정 거래소의 API가 점검 중이거나 장애 상태인 경우, Next.js Route Handler SHALL 마지막으로 캐시된 데이터를 반환하고 데이터의 최신성을 안내한다.

**[NestJS 백그라운드 서비스]**

9. WHILE NestJS 백그라운드 서비스가 운영 중일 때, NestJS SHALL 거래소 WebSocket API에 상시 연결하여 실시간 시세 데이터를 수신한다 (시세 데이터는 공개 데이터이므로 API Key가 불필요하다).
10. WHEN 실시간 시세 데이터가 수신되면, NestJS 백그라운드 서비스 SHALL 수신한 시세 데이터를 클라이언트에 WebSocket/SSE로 전달한다.
11. WHILE NestJS 백그라운드 서비스가 운영 중일 때, NestJS SHALL 사용자가 설정한 가격 알림 조건을 공개 시세 데이터 기반으로 상시 모니터링한다.
12. WHEN 클라이언트가 포트폴리오 스냅샷을 전송하면, NestJS 백그라운드 서비스 SHALL 해당 스냅샷 데이터를 DB에 저장한다.
13. WHEN 정기 리포트 생성 주기가 도래하면, NestJS 백그라운드 서비스 SHALL cron 스케줄러를 통해 자동으로 리포트를 생성한다.

**[포트폴리오 스냅샷 수집]**

14. WHEN 포트폴리오 스냅샷 수집이 필요할 때, 서버에 API Key가 없으므로 서버 측 cron에 의한 자동 수집은 불가하다. 대신 클라이언트가 대시보드에 접속할 때마다 현재 포트폴리오 스냅샷을 NestJS에 전송하여 DB에 저장하는 방식으로 스냅샷을 축적한다.
15. WHEN 클라이언트가 대시보드에 접속하여 포트폴리오 데이터를 조회하면, 클라이언트 SHALL 조회된 포트폴리오 스냅샷 데이터를 NestJS 백엔드에 전송하여 DB에 저장한다.

## 비기능 요구사항

### NF1. 성능

1. WHEN 대시보드 페이지가 요청되면, 시스템 SHALL 3초 이내에 초기 콘텐츠를 렌더링한다 (First Contentful Paint).
2. WHEN 거래소 API를 호출하면, 시스템 SHALL 개별 거래소 응답 대기 시간을 10초로 제한하고, 타임아웃 시 적절한 오류 처리를 수행한다.
3. WHEN 여러 거래소의 데이터를 조회하면, 시스템 SHALL 병렬로 API를 호출하여 전체 응답 시간을 최소화한다.
4. WHILE 시스템이 운영 중일 때, 시스템 SHALL 거래소 API Rate Limit을 준수하여 요청을 조절한다.

### NF2. 확장성

1. WHEN 새로운 거래소를 추가해야 할 때, 시스템 SHALL 거래소 어댑터 패턴을 통해 기존 코드 변경 없이 새로운 거래소를 통합할 수 있도록 설계한다.
2. WHEN 시스템 아키텍처를 설계할 때, 시스템 SHALL Next.js(CORS 프록시 및 프론트엔드)와 NestJS(백그라운드 서비스: WebSocket 시세 수신, DB 저장, 알림 모니터링, cron 작업)의 역할을 명확히 분리하여 각각 독립적으로 스케일링 및 유지보수가 가능하도록 API 인터페이스를 설계한다.
3. WHEN 운영 환경을 구성할 때, 시스템 SHALL OCI 단일 환경에서 Docker Compose를 통해 nginx, Next.js, NestJS, MySQL을 컨테이너로 운영한다.
4. WHEN CI/CD 파이프라인을 구성할 때, 시스템 SHALL GitHub Actions를 통해 자동 빌드 및 배포를 수행한다.
5. WHEN 모노레포 구조를 채택할 때, 시스템 SHALL apps/web(프론트엔드) 패키지와 apps/api(백엔드) 패키지를 독립적으로 빌드 및 배포할 수 있도록 구성한다.

### NF3. 가용성 및 안정성

1. WHILE 시스템이 운영 중일 때, 시스템 SHALL 99% 이상의 가용성을 유지한다 (거래소 API 자체 장애 제외).
2. IF 특정 거래소의 API가 장애 상태이면, 시스템 SHALL 나머지 거래소의 서비스를 정상적으로 제공한다 (Graceful Degradation).
3. WHEN 예기치 못한 오류가 발생하면, 시스템 SHALL 오류를 로깅하고 사용자에게 서비스 복구 안내를 제공한다.

### NF4. 접근성

1. WHEN 웹 페이지가 렌더링되면, 시스템 SHALL WCAG 2.1 AA 수준의 접근성 기준을 준수한다.
2. WHEN 금액/수치 데이터가 표시되면, 시스템 SHALL 스크린 리더가 올바르게 읽을 수 있도록 적절한 ARIA 레이블을 제공한다.

### NF5. 국제화 준비

1. WHEN 시스템이 설계될 때, 시스템 SHALL 한국어를 기본 언어로 지원하되, 향후 다국어(영어 등) 지원이 가능하도록 텍스트 리소스를 분리한다.
2. WHEN 통화 데이터가 표시되면, 시스템 SHALL KRW를 기본 통화로 사용하되, 향후 USD 등 다른 통화 표시를 추가할 수 있는 구조를 유지한다.

### NF6. 인프라 및 배포

1. WHEN 시스템을 배포할 때, 시스템 SHALL OCI Always Free Tier VM(ARM)에 배포하여 운영 비용을 최소화한다.
2. WHEN 웹 트래픽을 처리할 때, nginx SHALL 리버스 프록시로서 클라이언트 요청을 Next.js(port 3000)와 NestJS(port 4000)로 적절히 라우팅한다.
3. IF 도메인이 확보된 경우, nginx SHALL Let's Encrypt를 통한 SSL 터미네이션을 수행하여 모든 통신을 HTTPS로 암호화한다. 초기에는 도메인 없이 IP + HTTP로 운영 가능하며, API Key가 서버로 전송되지 않으므로 HTTP 환경에서도 보안상 문제가 없다.
4. WHEN 코드가 main 브랜치에 병합되면, GitHub Actions SHALL 자동으로 빌드, 테스트, 배포 파이프라인을 실행하여 OCI VM에 배포한다.
5. WHILE 시스템이 OCI에서 운영 중일 때, 시스템 SHALL OCI Budget Alert를 설정하여 예상치 못한 과금을 방지한다.
6. IF CDN 및 DNS 최적화가 필요한 경우, 시스템 SHALL Cloudflare를 CDN 및 DNS로 활용하여 성능과 보안을 강화할 수 있다.

## 향후 확장 사항 (범위 외 참고)

아래 항목은 현재 요구사항 범위에는 포함되지 않으나, 향후 로드맵으로 고려한다.

- **포트폴리오 변동 알림**: 포트폴리오 총액 변동 시 알림 (서버사이드 API Key 저장 옵션 추가 후 구현)
- **해외 거래소 연동**: 바이낸스, 코인베이스, 크라켄 등 글로벌 거래소 API 통합
- **거래(매매) 기능**: API를 통한 주문 실행 (시장가/지정가 매수/매도)
- **온체인 지갑 조회**: 메타마스크 등 지갑 주소 연결을 통한 온체인 자산 통합 조회
- **DeFi 프로토콜 통합**: Uniswap, Aave 등 DeFi 포지션 조회
- **소셜/커뮤니티 기능**: 포트폴리오 공유(익명 옵션), 투자 전략 토론
- **세금 신고 리포트**: 국내 세법 기준 암호화폐 양도소득 계산 및 신고 자료 생성
- **AI 기반 인사이트**: 포트폴리오 리밸런싱 제안, 시장 동향 요약
